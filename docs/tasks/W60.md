# W60 — Медиаредактор Redactix (замена TinyMCE для статей/страниц)

**Дата:** 2026-10-29
**Статус:** запланировано
**Приоритет:** средний
**Связано:** W3 (заменено W58), W47 (почта), W48 (Collabora), W58 (X-Accel), W59 (просмотр).

---

## 1. ЦЕЛЬ

Заменить TinyMCE на Redactix для статей и страниц: медиаредактор с блоками (текст, изображения, галерея, видео, embed, документы), простой для «слабого пользователя».

Задачи:
- Убрать «жёсткую привязку к строке»; вставка медиа — отдельными блоками.
- Фото: миниатюры с лайтбоксом (использовать существующий лайтбокс проекта).
- Видео: HTML5-плеер и embed (YouTube, VK, Vimeo и т.д.).
- Документы: список плитками (из облака).
- Убрать отдельный блок «альбомы под статьёй» — заменить галереей внутри контента.
- Сохранить привязку файлов к облаку (ContentFile, W58) — при сохранении статьи регистрировать использованные файлы.

## 2. ЧТО УЖЕ ЕСТЬ (БАЗА)

- **TinyMCE** — текущий редактор статей/страниц (framework/static/tinymce). Для почты (W47) остаётся.
- **Облако**: CloudFile, ContentFile (W58), /files/<id> (X-Accel), internal API (X-Internal-Key).
- **Лайтбокс**: самописный, core/templates/core_base.html (блок lightbox) + триггеры data-lightbox; навигация prev/next.
- **Альбомы под статьёй**: отдельный блок в article.html (Photo/Album) — переделать в галерею внутри контента.
- **Просмотр офисных файлов**: /view/<id> (W59), Collabora (W48).

## 4. АРХИТЕКТУРА ИНТЕГРАЦИИ

### 4.1. Адаптер загрузки (framework → cloud)

Redactix требует от эндпоинта загрузки JSON-формат: `success, src, srcset, alt, title, caption`.

В framework — два маршрута-адаптера (только admin/editor):
- `POST /admin/redactix/upload` — принимает файл, сохраняет в облако (CloudFile + файловая система, как `/admin/api/cloud-*` и `_archive_user_mailboxes_to_admin`), возвращает JSON для Redactix.
- `GET /admin/redactix/browse` — список файлов облака (для галереи Redactix), в формате, который ждёт редактор.

Важно: framework работает с CloudFile напрямую (общая БД + CLOUD_DATA_ROOT), без HTTP-прокси в cloud — как существующие `/admin/api/cloud-tree`, `/admin/api/cloud-folder`, `_archive_user_mailboxes_to_admin`.

### 4.2. Парсинг контента при сохранении

При сохранении статьи/страницы framework парсит HTML и находит: `<img src>`, `<video src>`, `<a href>` на файлы облака.
Найденные файлы регистрируются в ContentFile (W58) и/или FileUsage — через существующий content_service.

### 4.3. Рендер на публичной части

Article.content/Page.content остаётся Text (HTML). На публичной части — `content|safe` + CSS для блоков Redactix (figure.redactix-video, figure.redactix-embed и т.д.).

## 5. СИСТЕМНЫЕ ПАПКИ СТАТЕЙ И СТРАНИЦ

### 5.1. Принцип

При нажатии «Создать статью/страницу» **сразу** создаётся запись в БД (`is_published=False`) — решает проблему «курицы и яйца» (файлы можно грузить до первого сохранения).

- `Article.title` = `untitled_<id>_<dd.mm.yy>` (например, `untitled_42_30.10.26`), в форме поле пустое с плейсхолдером «статья без названия», обязательно к заполнению.
- `Page` — аналогично (`untitled_<id>_<dd.mm.yy>`, плейсхолдер «страница без названия»).
- В облаке создаётся папка `Статьи/untitled_<id>_<dd.mm.yy>` (для страниц — `Страницы/...`), у каждого admin/editor своя (owner_id).
- Архивные — `Статьи/_archive/<имя>` и `Страницы/_archive/<имя>` (служебные, скрыты из обычного дерева).

### 5.2. Сценарии

**Сценарий 1 (успех).** Создать → заполнить поля, контент, загрузить файлы → Сохранить. Статья сохраняется с заголовком («День куриного яйца»), папка в облаке переименовывается в это же имя.

**Сценарий 2 (сбой/перезагрузка).** Создать → вырубили свет. После включения в списке статей есть `untitled_<id>_<dd.mm.yy>` (и такая же папка в облаке). Пользователь открывает, редактирует, сохраняет — как в сценарии 1.

**Сценарий 3 (удаление черновика).** Создать → заполнить, загрузить файлы → передумал, удаляет. Сайт просит подтверждение: «У статьи есть прикреплённые файлы, продолжить удаление?». При подтверждении:
- статья удаляется;
- папка уходит в **корзину облака** с именем `article_unnamed_<id>_<dd.mm.yy>` (для страниц — `page_unnamed_<id>_<dd.mm.yy`), файлы восстановимы.

### 5.3. Переименование

Переименование статьи/страницы = переименование папки (папка всегда = текущий заголовок). Безопасно: файлы отдаются по `/files/<id>`, не по пути.

### 5.4. Логика

Статьи и страницы — одинаковая логика. Системные папки («Статьи», «Страницы») — только у admin/editor.

### 5.5. UI «Прикреплено» в облаке

- Вкладки: «Статьи» / «Страницы».
- В каждой — подразделы «Активные» / «Архивные».
- Сортировка по дате/имени.
- Корзина — общая (существующая).

### 5.6. Состояния и симметрия

Статья/страница и папка — одна сущность; действия симметричны с обеих сторон (админка ↔ облако):

| Состояние | Статья/страница | Папка в облаке |
|---|---|---|
| Активна | в основном списке | `Статьи/<имя>` |
| Архив | вкладка «Архив» в админке | `Статьи/_archive/<имя>` |
| Корзина | удалена, восстановима | общая корзина облака |
| Удалена навсегда | после очистки корзины | — |

### 5.7. Архивация

- **Только вручную**, массово: чекбоксы в списке статей → «В архив» (можно выбрать одну).
- **Автоархивации нет.** `SiteSettings.archive_after_days` и `archive_retention_days` — удалить (миграция). `Article.archived_at` — оставить (факт архивации).
- **Восстановление:** кнопка «Восстановить» во вкладке «Архив» + массово (симметрично).
- **Публичная часть:** архивная статья доступна по прямой ссылке (`/article/<id>`), но не в списках и не в поиске. На странице — плашка «Статья в архиве» (видна всем).
- **Файлы архивной статьи** доступны (прямые ссылки `/files/<id>`, `/media/<id>` работают).
- **ContentFile / FileUsage** не меняются (привязки сохраняются).

### 5.8. Удаление навсегда

- «Удалить навсегда» (из корзины) → статья, папка и файлы удаляются безвозвратно.
- **Предупреждение:** если файлы используются в других статьях/страницах (`ContentFile`/`FileUsage`) — «файл используется в статье X, всё равно удалить?».
- При подтверждении: файлы удаляются, **упоминания в других статьях вычищаются** из HTML (парсинг по `ContentFile`/`FileUsage`; теги `<img>/<video>/<a>` на этот файл удаляются). Битых ссылок не остаётся.

## 7. ДОКУМЕНТЫ ПЛИТКАМИ

В Redactix нет готового блока для списка документов. Решение: **переиспользовать существующую модалку выбора файлов** (`attached-files.js`, W58) — открывается из редактора, пользователь выбирает документы, вставляется блок-список.

### 7.1. Состав

- Только документы: pdf, txt, архивы (zip/rar/7z/tar.gz), офисные (docx/xlsx/pptx). Без картинок/видео.
- Фильтр в модалке: только эти типы.

### 7.2. Вид — карточки (сетка)

┌─────────────────┐
│ 📄 │
│ Отчёт.pdf │
│ 2.4 МБ │
│ [ Открыть ] │
└─────────────────┘

Карточка: иконка типа, имя, размер, кнопка действия.

### 7.3. Действие по типу

| Тип файла | Кнопка | Куда |
|---|---|---|
| docx, xlsx, pptx | «Открыть» | `/view/<id>` (Collabora read-only, W59) |
| pdf, txt, архивы | «Скачать» | `/files/<id>` (X-Accel) |

- Определение по MIME/расширению.
- **Фолбэк:** если Collabora недоступна — для офисных тоже «Скачать».

## 8. МИГРАЦИЯ И СОВМЕСТИМОСТЬ

- **Поля:** `Article.cloud_folder_id`, `Page.cloud_folder_id` — FK на `CloudFile` (явная связь с папкой).
- **SiteSettings:** удалить `archive_after_days`, `archive_retention_days` (миграция).
- **`Article.archived_at`** — оставить.
- **Старые статьи/страницы** (HTML от TinyMCE, без папок) — живут как есть; папка создаётся при первом сохранении/загрузке.
- **TinyMCE** остаётся для почты; для статей/страниц — убирается.
- **Отдельный блок альбомов под статьёй** — убрать после внедрения галереи.

## 9. ЭТАПЫ И ОЦЕНКА

1. Модель/миграция: `cloud_folder_id` (Article/Page), удаление archive_* — 1–2 дня.
2. Системные папки: создание при create, переименование, `_archive`, корзина, симметрия — 3–5 дней.
3. Адаптер upload/browse (framework, напрямую CloudFile) — 2–3 дня.
4. Внедрение Redactix в формы Article/Page — 2–3 дня.
5. Парсинг HTML при сохранении (ContentFile/FileUsage) — 1–2 дня.
6. Галерея + лайтбокс — 1–2 дня.
7. Блок «Документы плитками» (модалка W58 + карточки + Collabora/скачать) — 2–3 дня.
8. Архив/корзина UI (вкладки, массовые действия, предупреждения) — 3–4 дня.
9. Удаление навсегда (с вычисткой упоминаний) — 1–2 дня.
10. Полировка (стили, адаптив), тесты — 2–3 дня.

Итого: ~3–4 недели (уточняется при реализации).

## 10. РИСКИ И ОГРАНИЧЕНИЯ

- Redactix — молодой проект (меньше пользователей); код открыт, можно допиливать.
- Зависимость от стороннего API (upload/browse) — стабильность форматов.
- Кастомный блок документов требует написания плагина (vanilla JS).
- TinyMCE остаётся в проекте (для почты) — дублирование библиотек (не критично).
